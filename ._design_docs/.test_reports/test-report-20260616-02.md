## Findings

### F-16-TR-06: Bug fix does not resolve checkpoint admission (NEW, blocking)

- Severity: blocking (drives the FAIL verdict on PC1, PC2, PC3, PC4, PC5, PC6)
- Evidence: server.err.log after 2 chat-completion requests:
  `cache metadata: source=openai-chat
  method=rendered-text-boundary-inference degraded=rendered text
  boundary inference tokens=61 boundaries=12` (12 boundaries =
  5 system + 3 user + 3 assistant + 1 end-of-prompt; the new
  per-message prompt-span boundaries ARE emitted, 3 added).
  Followed by
  `save_slot: hybrid cache: checkpoint admission skipped
  (missing checkpoint boundary metadata)`.
  `cache_checkpoint_admissions_total=0`,
  `cache_checkpoint_admission_failures_total=1` after the first
  request. Same pattern on /completion (PC6):
  `cache_checkpoint_admission_failures_total=1` after first save,
  hits=0, misses=30, admissions=0.
  The MTP internal checkpoint is at `n_tokens=11` (end of user
  message). The fix adds per-message `[0, token_end]` boundaries
  with `token_end` matching the user message end (11). The matching
  loop at `server-cache-hybrid.cpp:3066-3081` iterates
  `source_metadata->boundaries` looking for a boundary with
  `token_end == 11`. The user MESSAGE_END at `[2, 11]` (role="user")
  is the first match. The matching loop sets
  `descriptor.boundary_id = "user"`,
  `descriptor.checkpoint_boundary_kind = MESSAGE_END`,
  `descriptor.boundary_checksum = checksum(2, 11)`. The strict
  validator at lines 2988-3001 looks for a boundary with
  type=MESSAGE_END, metadata="user", token_end=11,
  checksum=checksum(2, 11). The user MESSAGE_END boundary matches
  all four fields. The checksum recompute
  `cache_token_span_checksum(entry.tokens, 2, 11)` should equal
  the boundary.checksum. Despite this, the strict validator
  returns `missing checkpoint boundary metadata` from line 2984,
  which is the pre-loop check that rejects when
  `descriptor.boundary_id.empty() || descriptor.boundary_checksum == 0 ||
  descriptor.checkpoint_boundary_kind < 0`. This implies the
  matching loop did NOT find a boundary, leaving the descriptor
  fields at their default values (boundary_id="", boundary_checksum=0,
  checkpoint_boundary_kind=-1).
- Root cause hypothesis: the matching loop's boundary iteration
  may be operating on a `source_metadata` whose boundaries are
  empty or differ from the chat path's 12 boundaries. The
  `entry.metadata` is set in `admit_entry_with_payload` from the
  chat metadata (12 boundaries), but the matching loop's
  `source_metadata` is `metadata ? metadata : &entry.metadata`
  where `metadata` is `&entry.metadata` from
  `admit_latest_checkpoint`. The entry's metadata should have 12
  boundaries. Possible issue: the entry's metadata is being cleared
  or replaced between `admit_entry_with_payload` and
  `admit_latest_checkpoint` (no evidence in source; both are
  called sequentially in `save_slot` without intermediate
  `entry.metadata` mutation).
- Action: Developer handoff for bug-fix loop iteration 2. Three
  closure options (in priority order):
  1. Add debug logging to the matching loop in
     `server-cache-hybrid.cpp:3066-3081` to confirm which
     boundaries are iterated and why none match `token_end=11`.
     The matching loop's first skip condition
     `boundary.checksum == 0` is the most likely cause: if any
     boundary in the list has checksum 0, it's skipped. Verify
     that all 12 chat-path boundaries have non-zero checksums.
  2. Inspect the chat-path `add_span` call at
     `server-context.cpp:4474` to confirm
     `msg_end_checksum` is non-zero for the user message
     (token_end=11). If `cache_metadata_checksum(tokens, 0, 11)`
     returns 0, the new boundary is skipped by the matching loop.
  3. Reclassify the MTP fixture as `NOT-IN-SCOPE` for
     `/v1/chat/completions` exact-blob restore, per Stage 15
     Manager decision 1, and document the
     `B02/B05/B06 NOT-IN-SCOPE` reclassification as still
     active.
