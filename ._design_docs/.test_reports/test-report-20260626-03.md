## D-EXEC-24-03 root cause analysis (updated)

Prior hypothesis (from -02-fixes.md): argv use-after-free in Stage 26 SEH plumbing was masking D-EXEC-24-03 reproduction because every server launch with `--crash-dump-dir` crashed at startup before reaching the request loop.

This run (-03) with D-EXEC-26-02 fix applied:

- Server reaches request loop successfully (S02 native, S02 hybrid, S03 native all PASS at 2544, 1444, 1526 reqs respectively)
- D-EXEC-24-03 reproduces at exactly request 258 with same signature as -01
- Server crashes silently mid-leg without raising Win32 exception (SEH dump dir empty)
- Cache state at death same as -01 (637 tokens, 502.5 MiB)

Conclusion: **D-EXEC-24-03 is a separate bug, not the argv use-after-free.** The use-after-free was a different failure mode that only manifested when `--crash-dump-dir` was passed at startup; it masked the request-loop crash in -02 by killing the server before any request. With that startup bug fixed, the request-loop crash reproduces at the same point.

### Possible D-EXEC-24-03 mechanisms (open, not diagnosed)

- Silent worker-thread death that does not raise Win32 EXCEPTION (e.g., longjmp, abort, exit, endthreadex, fast-fail STATUS_STACK_BUFFER_OVERRUN suppressed)
- Loss of parent process handle or socket without raising exception
- CUDA driver call returning non-zero status with subsequent process termination not via SEH
- Hybrid cache state corruption at request 257-258 boundary (last OK is `s03-exact-0-0` with cache_n=15; first failed is `s03-exact-0-1` immediately after)
- 637-token cache state at death is far below 4096 token limit; 502.5 MiB is at 502/512 = 98.1% of MiB budget (over 95% may trigger eviction race)

Evidence to seek next:

1. Add Win32 ErrorMode / verbose crash diagnostics (WER local dumps)
2. Capture periodic process state snapshots before death (e.g., every 10 reqs)
3. Add `std::terminate_handler` and `_set_abort_behavior` to catch abort
4. Add CUDA driver call logging around request 257-258 boundary
